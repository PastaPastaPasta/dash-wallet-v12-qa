1. What changed, and where QA focus goes

The branch is the dashj → Dash Platform Kotlin SDK cutover for L1 (SPV) plus a large memory/sync recovery effort. Non-doc change areas by volume:

  1. wallet/…/service/platform/sdk (56 files): CutoverStateMachine (DUAL_RUNNING → READY_OBSERVED → CUT_OVER → SETTLED), SDK bind/retry, L1 shadow SPV engine, filter-stall watchdog + engine restart (616ac58ff), replay memory telemetry, watermark persistence.
  2. Startup / lifecycle: startup breadcrumbs, wallet-load budget, wallet-file-size guard, process-exit-reason logging, foreground service promise, boot/alarm scheduling, "rotating a screen must not lock the wallet", auto-logout on background.
  3. Post-cutover data seam: home screen, tx list, tx detail, balance, send authority, send-all drain, instant receives, metadata all served by the SDK instead of dashj. Anything that displays or spends money is affected.
  4. DashPay / usernames / invites (35 + 11 + 12 files): username creation routing (contested vs non-contested), voting tile, invites via shielded pool, contact request coverage, DIP-15 friend chains (20-address cap issue filed upstream), identity retry.
  5. Shielded balance (new UI: ui/shielded/*): shield / unshield transfers, stall notice + watchdog, fees.
  6. Restore / reset / migration: wallet wipe sequence, restore-from-seed on SDK, Room migrations (v22).
  7. common/ (120 files) + integrations (maya 44, crowdnode 39, coinbase 23, uphold 5, exploredash 15): shared money formatting shims, BIP39/WIF utilities, CrowdNode deposit-all, Maya/SwapKit sells, Coinbase fiat-option crash fix.
  8. Build: minSdk 24 → 29, 64-bit only (arm64-v8a, x86_64), APK ~300 MB (two ~50 MB native SDK libs), versionCode 12000000, BIP70 dashj implementation deleted (SDK route only), grpc-netty-shaded keep rules.

So: the core risk is sync/cutover/memory; the secondary risk is every screen that reads balance or transactions from the new seam; the tertiary risk is regressions in untouched-looking flows that now sit on minSdk 29 and R8 keep-rule changes.

2. Test matrix

Each test gets an ID, a dedicated emulator, an evidence folder, and a PASS/FAIL/BLOCKED verdict with the exact evidence file names. All tests capture: screenshots at each named step, wallet.log pull at the end, logcat for the whole run, and a memory CSV sampled every 60 s (qa-app.sh <serial> memlog).

Tier A — the three scenarios from the brief (must run)

A1 — Fresh wallet, shield, username, reset, restore (emulator dw-qa1) 1. Install fix APK, create new wallet, set PIN 1234, view and record the 12-word recovery phrase (evidence: screenshot + typed into notes.md; this is a throwaway testnet wallet). 2. Get a receive address, fund via faucet (1 tDASH covers the 0.11 minimum). Wait for the receive to show and be confirmed/InstantSend-locked. Record txid and balance. 3. Send all balance to shielded (More › Shielded balance › Shield, or the equivalent entry). Record fee, resulting shielded and transparent balances, tx list. 4. Create a non-contested username (fee 0.03 tDASH from Constants.DASH_PAY_FEE; funded from the shielded pool, min 0.035). Wait for identity registration + DPNS to complete. Screenshot the home/profile showing the username. Verify on the Platform explorer. 5. Screenshot balance + transaction list (this is the reference for step 7). 6. More › Security › Reset wallet (confirm PIN), then Restore from recovery phrase with the phrase from step 1. 7. Wait for sync to finish. Assert: balances (transparent + shielded) and transaction list identical to step 5; username re-associated. Diff the two screenshots and the two wallet.log balance lines. 8. Negative checks along the way: wrong PIN on reset, malformed seed word, back-navigation from each screen does not crash.

A2 — Restore the reference seed on a clean install, does sync finish (emulator dw-qa2) Seed: job flower agree lyrics industry note boost finger buddy dog exact fat. Expected balance 107.43173749 tDASH. 1. Install fix APK, restore from seed, set PIN. 2. Watch sync to 100% (grep-log 'percentageSync|cutover state|L1 shadow SPV started|filter-stall|idling detected|restart'). Sample memory every 60 s. Record: time to first block, time to 100%, number of engine restarts, any "filter cursor has sat at" watchdog lines, any "idling detected" lines, peak PSS / native heap. 3. Assert final balance == 107.43173749 and tx list populated. Cross-check against the insight explorer for the first few receive addresses (get them from the wallet's address book / xpub). 4. Stall probes: after 100%, background the app 5 min, foreground; kill process, relaunch; toggle airplane mode off/on mid-sync (do this on a second restore pass so the clean pass stays clean).

A3 — Upgrade path master 11.9.0 → fix 12.0.0 (emulator dw-qa3) 1. Install master APK, restore the reference seed, set PIN, let dashj sync start and run ~60 min (or until it has real progress; record % and block height). 2. adb install -r the fix APK over it (same signing key). Launch. This crosses the cutover boundary (FIRST_CUTOVER_VERSION_CODE=12000000). 3. Assert in wallet.log: cutover state DUAL_RUNNING -> … -> CUT_OVER on this launch, exactly one L1 shadow SPV started, no starting peergroup (dashj) line, the one-time "A one-time sync is needed" explainer shown once (screenshot), no OverlappingFileLockException, no idling detected while replaying. 4. Sync to 100%, balance == 107.43173749, memory CSV shows no runaway (compare against plan targets: native heap bounded, JVM idle well under the heap), no LMK/OOM kill (qa-app.sh oom, dumpsys activity exit-info). 5. Repeat step 3's assertions after a process kill + relaunch (SETTLED state reached, no second explainer). 6. Variant A3b (same emulator after A3, or dw-qa3 reset): upgrade while the device is locked (set a device PIN, lock, install -r, launch via am start, then unlock) — the pending-bind notification path, bind within 5 s of unlock.

Tier B — sync/cutover/memory beyond the brief

  • B1 Low-memory pressure during replay (dw-qa2 after A2): fresh restore of the reference seed on an AVD with hw.ramSize=1536; send am send-trim-memory RUNNING_CRITICAL every 2 min; assert the replay resumes from its watermark (log "syncedHeight"), engine restart count, no data loss.
  • B2 Kill/restart torture: during A2's replay, am force-stop at 25/50/75%; each relaunch must resume without losing more than ~5,000 blocks (plan target).
  • B3 Network flap: airplane mode 2 min on/off ×3 during replay; peers reconnect, filter cursor moves again, watchdog behaves.
  • B4 Background/idle: after 100%, leave app backgrounded 30 min; no "idling detected … stopping service" loops, service count sane, no wakelock storm in dumpsys batterystats.
  • B5 Tools › dashj sync toggle (if present in Tools on this build): turning it on is the only thing that should produce a dashj peergroup start.

3. Execution model

  • One Opus subagent per emulator/test-stream, run in parallel: Stream 1 = A1 → C → D; Stream 2 = A2 → B; Stream 3 = A3 → A3b → E8. A fourth Opus agent runs E (regression sweep) on whichever emulator frees first, and E9 on the host.
  • Long waits (sync ~1 h) are handled inside the agent with poll loops of qa-app.sh grep-log, memory sampling, and periodic screenshots. Agents must never fabricate progress: every claim cites a file under $QA_EVIDENCE.
  • Agents report using the template in $QA_ROOT/REPORT-TEMPLATE.md. I merge the reports into $QA_ROOT/QA-REPORT.md with a defect list (ID, severity, repro, evidence, log excerpt, suspected commit).
  • Severity: S1 funds/balance wrong or lost, crash loop, sync never finishes; S2 sync stalls but recovers only with user action, memory kill, wrong tx history; S3 UI/flow bug with workaround; S4 cosmetic.

4. Open items / assumptions

  • Faucet gives 1 tDASH per request; the brief's 0.11 minimum is satisfied by one request per wallet.
  • The reference-seed balance 107.43173749 is taken from the brief; if the wallet has received funds since, the A2/A3 assertion becomes "balance ≥ 107.43173749 and equals the explorer sum".
  • The emulator has no Google account, so Google Drive / email sending from Contact Support is verified only to the share sheet.
  • The master baseline is master @ bde52b520 (11.9.0, versionCode 11090002), which satisfies "11.9.0 or higher".
